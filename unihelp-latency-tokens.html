UniHelp performance briefing · 19 Sep 2026

How UniHelp cuts latency and token usage

The system does not make campus lookups cheaper by shrinking prompts. It skips the language model whenever a deterministic path can answer the request. On the 18-query benchmark that is the difference between a 27-second mean and a 5.6-second mean.

The rule Use an LLM only to decide among ambiguous agents, to run a write or a tool loop that cannot be parsed, or to phrase a multi-result reply. Mess, bus, notices, and timetable lookups with a clear catalog match never call a model. A single-agent plan is a function call, not a planner-plus-executor chat.

Where the time went

The naive campus-agent stack paid for three LLM round-trips on almost every request: planner (which agent?), executor (which tool?), then the domain agent (call the tool and write the answer). Independent two-part queries stacked those loops sequentially and could sit near two minutes.

UniHelp inverts that. Most traffic never reaches a model. Remaining LLM work is either a capped fast-tier JSON plan or one user-facing completion.

Mechanisms

Five layers that remove LLM work

1. Catalog-driven fast parse — the zero-token path

fast_parse.py turns an unambiguous mess, bus, notice, or timetable question into a fully populated argument dict. Names and aliases come from the org profile (hostels, buses, meals), not from a hardcoded guess. If the query is a write, names two hostels, or has an unparseable date, the parser returns None and the agent falls through to the model.

Example hit
“What’s today’s breakfast at Kalam hostel?”

Parser extracts hostel + meal + date, get_menu() runs, a template formats the reply. 0 LLM calls, 0 tokens, <2 ms.

Same for
Bus, notices, timetable

“Bus 02 schedule”, “show today’s notices”, “what’s my timetable today” all bypass the agent tool loop the same way.

Conservative miss
Do not guess

A mess query with no hostel asks which hostel from the catalog. Mixed timing language (“next departure”) falls through to the LLM.

2. Planner shortcuts — skip the routing model

The planner used to be an LLM call on every request. It now tries deterministic plans first, in this order:

  1. Conditionals — regex splits if / then / else / unless into gated tasks with structured depends_on. Nested or ambiguous connectives still go to the model.
  2. One-agent keywords — “dinner at Kalam” matches only mess → a single task, no planner LLM.
  3. Independent “and” — “dinner at Kalam and the Bus 02 schedule” used to miss the one-agent path (two domains) and hit the planner. A thinking fast-model call billed ~8k hidden completion tokens and ~140s for a 300-character JSON plan. The splitter now emits two independent tasks when each clause maps to a distinct agent.

Only leftover ambiguous text calls LLM_FAST_MODEL, with max_tokens=800 and gateway reasoning disabled. That stops a “fast” model from emitting a long hidden trace before a tiny JSON plan.

3. Direct executor dispatch — no tool-calling loop to pick the agent

The planner already names the agent. The executor is a dictionary lookup, not a second model that re-selects among seven tools.

  • Empty or unsupported plans return the planner message immediately.
  • A single-task plan calls that agent and returns its string. No executor LLM.
  • A gated follow-up is skipped when the condition fails, so attendance below a threshold never pays for a complaint or timetable call that should not run.
  • After skips, if only one result remains, that result is returned. Synthesis is one completion, and only when two or more lookups actually ran.

The old executor prompt taught a tool-calling model how to pick among seven agents. That text is gone. Dispatch does not need it; synthesis only combines already-fetched results.

4. Model tiering and prompt-prefix cache

Classification (planner JSON, YES/NO gates, value extraction) uses the fast tier. The reply the user reads — domain-agent final round and multi-task synthesis — stays on the strong tier so the answer is not truncated.

Every production call goes through chat_create with a stable system prompt marked cacheable. Identity (name, roll, role) is a later uncached message, so per-user fields do not bust the shared prefix. The gateway can reuse planner, mess, bus, and complaint prefixes instead of re-billing them as fresh input.

What this avoids
Paying full input tokens twice

Without a cache breakpoint, tool-loop agents resend the system prompt and tool schemas on every round. Cached prefixes turn that into a cheap cache-read on subsequent calls in the same window.

5. Data-path work that is not the LLM

When a fast-path query still needs Postgres, UniHelp keeps that off the critical path of a round-trip to a model:

Why latency falls more than call count

Mean LLM calls fell 35%, but mean latency and P95 each fell 80% because the missing calls were the expensive ones. A thinking fast-model planner could bill thousands of hidden tokens and sit near two minutes for a short JSON plan — that path is now skipped or capped at 800 tokens. Singles left the network entirely, so P50 is no longer mess/bus. Independent pairs no longer stack planner + two tool loops + a dump. Unmet gates skip the follow-up agent.
